# Subagent history correctness and TUI performance

Date: 2026-10-07. This is evidence for a future PR, not a release announcement.

## What this work changes

- Clear entries by both call ID and child-session identity. A child discovered as
  `tool:<call>`, `sub:<session>`, or another historical call alias must not return
  after one clear operation.
- Capture persisted entries, unpersisted cache entries, loaded history and
  discoverable child sessions; merge tombstones under the host storage lock.
- Await the clear commit before resetting the panel/cache or reporting success.
  Storage failures must not silently report a successful clear.
- Apply the same cleared-identity filter to scans, events, cached maps,
  enrichment and delayed persistence. Cleared parts are not "missing" entries
  that should trigger another recovery scan.
- Skip per-child database hydration for already-linked or cleared children.
  Keep normal discovery of new children and recovery of missing events.
- Ignore unrelated sessions' global tool/step events before repainting or
  scheduling a history scan. Keep V1's host-scoped event behavior.
- Reuse parsed unchanged history and immutable parent routing; remove the unused
  clock-driven copy of the entire entry list and unchanged-map saves.
- Run the animation clock only while there are active entries. `smooth` remains
  100 ms and `eco` remains 1 s. A collapsed panel still has a visible header, so
  active header animation must continue while collapsed.
- Share one breathing-color computation between the header and running rows.
  Animation ticks do not persist history or trigger a history scan.

### Relationship to PR #31

[PR #31](https://github.com/Hotakus/opencode-subagent-magazine/pull/31) concerned
prompt compaction and conservative clear-list maintenance, not animation.
Its 128-character persisted prompt limit and merge-safe persistence remain.

One intentional change: a canonical `sub:<session>` tombstone cannot be dropped
merely because the child is absent from the database. Historical tool parts can
still refer to that child, which otherwise allows an alias to resurrect it.

The first optimization attempt introduced an overly broad "stop when collapsed"
clock condition. That regression was corrected before the final benchmark.
The header's fixed running-dot color was pre-existing; the final build makes it
breathe in phase with the rows.

## Regression validation

`npm test`: **75 passed**. `npm run typecheck` and `npm run build`: passed.
`python3 tests/benchmark-tui.test.py`: **6 passed**, covering profile verification
for arbitrarily named worktrees, duplicate implementations, missing frames and
preservation of unrelated plugin directives/options in inline configuration.

Coverage includes stale writes from another TUI, cache/call aliases, parent vs.
child panel isolation, failed/async commits, exact call-to-child resolution,
repeat clear, missing host/database data, and new subagents after a clear.
Animation tests cover clock gating, two-second breathing, smooth/eco cadence,
and safe fallback for invalid theme colors/time.

### Tests inside an actual OpenCode TUI

Temporary validation plugins used synthetic sessions/messages and host **memory**
storage. No clear command was issued against real persisted history.

| Scenario | Smooth | Eco | Smooth again | After completion |
| --- | --- | --- | --- | --- |
| Open, running | Header and row changed color | 2 colors each | Smooth restored | Static |
| Collapsed, running | Header changed color | 2 header colors | Smooth restored | Static |
| Open, cancellation requested | Header and row changed color | 2 colors each | Smooth restored | Static |

All 12 scenario/phase checks passed. Every sampled phase recorded **zero storage
writes** caused by animation. The check verifies the actual rendered text-node
colors, not merely the timer function or a screenshot.

A separate real-TUI clear fixture passed: initial entry visible; one clear while
the message cache was unavailable; no return after late alias events and polls;
a genuinely new subagent visible and persisted normally.

## Method

Harness: [`scripts/benchmark-tui.py`](../../scripts/benchmark-tui.py).

- OpenCode CLI and shared service **2.0.22**, Linux kernel
  `6.11.0-26-generic`; Intel Xeon E5-2690 v3 @ 2.60 GHz, 48 logical CPUs.
- Same existing historical session and project directory in every trial.
  Before the experiment, that session had **281 persisted entries**: 280 done
  and 1 cancelled, with **no running entries**. The backed-up global subagent
  hot-store file was 497,574 bytes. These figures describe an idle historical
  panel; they are not an active-animation workload.
- All seven global plugin directives are explicitly retained in every temporary
  client, replacing only the selected subagent implementation: DCP, visual-cache,
  subagent-magazine, local shell-magazine, todolist, cut and deepseek-peak.
  Inline arrays replace global arrays; preserving this list is regression-tested.
  This is a **whole-TUI** measurement, not isolated plugin CPU attribution.
- Native animation setting enabled; persisted subagent refresh preference **`eco`**
  before and after every trial. The initial draft incorrectly said `smooth`;
  the recorded per-trial preferences are authoritative. npm 1.7.2 predates the
  refresh-mode option, so that release does not share the later eco behavior.
- Fresh temporary client in a 180-column × 52-row PTY for every sample.
- Tabs disabled process-locally in every variant. The global CLI configuration
  and service are not changed or restarted by the harness.
- 20-second warmup, then approximately 13 seconds of process sampling per trial.
- Three trials per variant; execution order varies between rounds.
- CPU: delta of process user + system ticks in `/proc/<pid>/stat`, divided by
  elapsed wall time, as **percent of one logical core**.
- Memory: arithmetic mean of the temporary client's RSS samples, in MiB.
- A ten-second `SIGPROF` CPU profile is collected within each sampling window.
  Its function URLs must identify the expected implementation, not another
  globally configured copy of the plugin.
- Bundle fingerprints, refresh mode and CLI configuration are checked for
  changes across the experiment.
- No prompts are sent, no synthetic model calls are made, and only temporary
  clients created by the harness are closed. Real history was backed up first.
  Ordinary plugin startup/events can still update their normal persistence.

## Final full-plugin results

All nine trial profiles were verified against the expected implementation.
CLI configuration and both local build fingerprints remained unchanged.

| Variant | Mean CPU, % of one core | CPU range | Mean RSS, MiB | RSS range, MiB |
| --- | ---: | ---: | ---: | ---: |
| Published npm 1.7.2 | 9.18 | 6.69–11.54 | 374.2 | 368.1–380.4 |
| Unmodified upstream 1.7.4 | 8.28 | 6.61–11.45 | 363.0 | 353.3–370.9 |
| Current build, including animation fix | 7.02 | 4.46–10.69 | 363.1 | 353.9–372.3 |

Means are arithmetic means of three trials per variant. Relative changes use
the unrounded means, not the rounded display values above.

- **Against the upstream PR base:** mean CPU was **15.2% lower**, a reduction
  of 1.26 percentage points of one core. Mean RSS was effectively unchanged
  (+0.17 MiB, +0.05%); this does **not** establish a RAM improvement.
- **Against the older npm release:** mean CPU was **23.5% lower**, a reduction
  of 2.16 percentage points. Mean RSS was 11.1 MiB (3.0%) lower. This includes
  upstream improvements predating the proposed changes and must not be credited
  entirely to the new PR.
- Variation is substantial: current CPU ranged from 4.46% to 10.69%, versus
  6.61% to 11.45% for upstream. Current was lower in each round, but overlapping
  ranges and three samples do not establish a universal or statistically proven
  improvement. These are observed means in this workload.
- The final build contains the animation fix, but there were **no running
  entries** in this workload. This does not quantify active smooth-animation
  overhead or prove unchanged performance during streaming.

The earlier ~31% comparison is superseded for the PR claim: it used npm 1.7.2
before the animation correction and did not separate existing upstream changes.
The initial final-build run (23.5% versus upstream, 40.8% versus npm) is also
superseded: it explicitly configured only the selected subagent plugin. Those
numbers must not be presented as full-plugin results.

### Profile verification and evidence

Sanitized per-trial measurements, build fingerprints and profile SHA-256 hashes
are in [`subagent-2026-10-07.json`](subagent-2026-10-07.json). Original profiles
and the original raw result are retained locally; the shared JSON contains no
session IDs, prompts, transcripts or absolute local paths.

An earlier harness run rejected the three upstream profiles because its URL
filter only collected paths containing the package name. The worktree directory
did not contain that name. Inspection showed the exact expected upstream bundle
URL in all three profiles. The filter was corrected and tested, then **all nine
unchanged profiles** were revalidated. A separate configuration review then
found that inline plugin arrays replace the global array, rather than merge.
The original run therefore did not preserve other external plugins. The
configuration helper was corrected and covered by three new tests, and a
**fresh complete nine-trial run** produced the final table and shared JSON.
Both original raw experiments remain preserved locally, including the initial
false verification flags. No old CPU/RSS values were edited or trials cherry-picked.

Profiles verify which build ran but do not isolate plugin cost. For example,
whole-TUI JSON parse/stringify self-time shares averaged 15.06% for npm, 10.25%
for upstream and 10.64% for current. These are sampled leaf-function shares,
not process CPU percentages; they do not support claiming that the new PR
uniformly reduced JSON work versus upstream.

A read-only post-run audit found all **281** pre-experiment historical entries
still present and identical to the backup, with no additional entries in that
session. No prompt or clear command was issued by the benchmark.

## Reproduction

Build the proposed checkout and an unmodified upstream worktree first. Use an
existing historical session that belongs to the selected project directory:

```sh
python3 scripts/benchmark-tui.py \
  --session EXISTING_SESSION_ID \
  --directory /path/to/session-project \
  --base /path/to/built-upstream-worktree \
  --local /path/to/built-proposed-checkout \
  --npm-version 1.7.2 \
  --rounds 3 \
  --output /tmp/opencode/subagent-benchmark.json
```

The output path must be new. The harness checks session existence before opening
a client because an absent `--session` ID can create a session.

## Interpretation limits

- The shared service, other TUIs, filesystem notifications and event traffic
  remain live. Trial ranges matter; three samples are not a universal guarantee
  or a statistically established speedup.
- This workload is a historical-session/sidebar measurement. It does **not**
  measure model throughput, typing latency, scroll latency, every session size,
  or the cost of continuously streaming active agents.
- The animation fixtures validate active/open/collapsed behavior and lack of
  animation-driven storage writes; their post-completion CPU profiles must not
  be presented as an active-animation performance benchmark.
- Existing prompt compaction, token-poll and refresh changes may explain part
  of the gap against npm 1.7.2. Attribute the **new work** using the unmodified
  upstream 1.7.4 comparison, not the larger old-release comparison alone.
- Do not publish session IDs, prompts, rendered transcripts, or absolute local
  profile paths in a PR. Keep original profiles locally for verification.
